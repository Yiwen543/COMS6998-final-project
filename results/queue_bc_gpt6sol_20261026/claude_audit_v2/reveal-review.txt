# Audit of the B/C queue pilot (`results/queue_bc_gpt6sol_20261026`)

**Bottom line:** the saved numbers are internally consistent, and B and C were held to the same conditions. The reported C-over-B result is small: C reached the 41/41 line target earlier in 2 of 6 paired runs, tied in 4 and was never later. This data does not show that the egg guard groups caused it. The groups were only in C's round-1 prompts. Neither early finish came from the read-only or write-only cases the groups describe.

## What I inspected and what I could not

**Inspected:**
- `REPORT.md`, `metadata.json`, `rounds.csv`, `target_costs.csv`
- all 48 lines of `calls.jsonl` (line 49 is empty, and there is no `failed-rounds.jsonl`)
- `egg-evidence.json`, and `typed-predicates.json` (the original-RTL section, the variant atoms, and variant targets for the first two processes)
- `prompt-original-C-1-3-1.json` in full
- `variant/{B,C}-1-2.vectors` and `variant/C-1-2.sim.log`
- the config, both scripts, the checker, the preflight doc, and the spec (as embedded in the prompt)

**Not inspected:**
- I could not recompute SHA-256 hashes, because no commands were allowed.
- `sim_main_queue.cpp`, the RTL files themselves (the original only as embedded in the prompt), the `.dat` coverage files, `rounds.jsonl`, and the plots.
- The round-1 prompts (111–121 KB), which were too large to read.
- Any saved per-pair Z3 log.
- A separate replay run. I could not list directories, and `replay/REPORT.md` does not exist. **I did not verify the results against a separate replay.**

## 1. Within-version equality — supported
- Each version is compiled once and both arms use that binary. Both share the 6-cycle seed (`INITIAL`), the same 4-cycle, 4-round and 2-retry budget, and the same checker.
- All 48 calls record `gpt-6-sol`, `low`, 4096 and 90 s.
- The vectors match the logged actions (`variant/C-1-2.vectors` matches `calls.jsonl` lines 37–38).
- Limitation: config `seed: 6998` is only used by `MockQueue`, so it had no effect on the live runs.

## 2. Raw coverage arrays and witness leakage — supported, partly by inference
- In code, B and C get the same `raw_points`, and C only adds an `egg_normalization` key (`queue_feedback.py:97-116`). The `raw_predicate` case annotation goes to both arms.
- Direct evidence: variant rep 1 round 1 has identical actions in both arms (`calls.jsonl` lines 25 and 37). The round-2 prompts differ by 42,679 − 42,371 = 308 bytes, which is the size of an empty egg block. Input tokens differ by 67 (14,049 vs 13,982). I did not byte-diff the files.
- No witness or reference vectors appear in the inspected prompt, and the reference vectors go only to `reference-ceiling.vectors`. The round-1 egg-block content is inferred from the code and from the byte differences (+3,806 original, +3,998 variant); I did not read it.

## 3. Guards, source spans, rewrites, read vs write — supported, with limits
- **Guards are full:** each guard includes reset, clear and enable, prior-case exclusions, and the case atom. For example, the write guard includes `(not p_0a14…)` before `p_d317…`.
- **Read and write are kept apart:** read (2'01, `{we,re}==1`) and write (2'10) are in separate e-classes 13 and 17. They match the comments "read only" / "write only" on lines 55–56.
- **Event context** (`negedge rst_ni`, `posedge clk_i`) is stored separately.
- **Source spans:** the 12 selected lines per version (55/56, 82/89, 124/125, 139/140, 154/155, 169/170) match the preflight doc.
- **Rewrite proof:** egg saturated after 5 iterations. Within one version, the 6 guards in a group have identical text in the original. The real rewriting is across versions (the variant's `(not (not (not p_2d08…)))` forms). The Z3 check only runs inside a `semantic_setup` assertion, and I saw no saved proof output.
- **Default-case spans are approximate.** These targets are not among the selected ones, e.g. `…:106:12:default` has source text `end`.

## 4. Tokens, retries, cycles and executions — supported
- Retries and failed attempts are 0, with 48/48 calls accepted on the first attempt.
- Spot checks of cumulative tokens match: original C rep 1 = 41,520 → 60,185 → 69,989 → 79,632; variant C rep 1 round 2 = 57,192.
- Replay is counted: each round's simulation has 6 + 4k checks (10/14/18/22), giving cumulative 10/24/42/64, and the code asserts this.
- **Tokens are not cost:** cached input counts as full input. Rep 2/3 round-1 calls were almost entirely cache hits (e.g. 39,790 of 39,793).
- **Discrepancy (presentation):** `REPORT.md` lines 31–34 round the mean simulation counts. Original B (3.67) shows as 4, and variant B (3.00) and variant C (2.67) both show as 3.

## 5. C versus B — what the data supports

**Supported:**
- Both arms reached 3/3 in each version, and final coverage is identical (41/41 line, 14/14 branch, full expression, 344/408 toggle).
- Mean tokens to target: C − B = −1,152 (original) and −3,895 (variant). Total spend at round 4: +2,092 (original) and −1,789 (variant).

**Not attributable to the guard groups:**
- In every run, round 1 already covered both the read-only and write-only cases. From round 2 on, C's groups are empty: `groups: []` appears directly in `prompt-original-C-1-3-1.json`, and the other runs are inferred from their round-1 actions.
- **Variant rep 1:** the arms had identical histories, and C's round-2 prompt added only an empty stub. C then reached 41 by issuing an enable-idle action (2'b00, line 108 `default`; `C-1-2.vectors` row 8). B did not (`rounds.csv` row 27 vs row 39).
- **Original rep 3:** C's round-1 gain (33 lines) came from a simultaneous read/write (2'b11; calls line 21). That case is not in the groups either.

**Repetitions are not independent:**
- Original C reps 1 and 3 produced identical actions in rounds 1 and 2 (calls lines 13 = 21, 14 = 22).
- Round-1 prompts were identical across reps and mostly cache hits.

**Pairing is arbitrary:** `REPORT.md` line 36 pairs B rep k with C rep k for the toggle counts. My recount (9 more / 3 fewer / 12 equal) matches.

## Corrections to the Stage 1 blind review
- **Round-1 "imbalance" (discrepancy):** this is the treatment itself. Round 1 is the only round where C's prompt carries the guard groups (+1,508 / +1,552 input tokens).
- **344/408 toggle plateau (explained):** the 64 missing points are `queue_data[3][31:0]` in both directions. They can't be reached once writing to a full queue is forbidden, and the reference run also stops at 344.
- **Duplicate trajectories across versions:** these are not a copy error. The logged actions differ (e.g. different data values) but the model chose almost the same stimulus.

## Checker and DUT — unresolved
Zero failures everywhere does not show the DUT is correct. The checker was written to match this RTL:
- **Capacity:** `CAPACITY = DEPTH-1` matches `FULL_THRESHOLD = DEPTH-2`, while the spec says DEPTH entries.
- **Read+write at empty:** the checker expects nothing to be kept, which matches what this RTL does.
- **Untested write:** writing a 4th item, which would overflow the 2-bit pointer, is rejected as illegal input, so it is never simulated.
- **Almost flags:** these are checked only on reset and clear.

A possible capacity or overflow defect is therefore defined away and stays untested.
