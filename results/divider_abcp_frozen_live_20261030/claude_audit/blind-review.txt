# Review of the W/X/Y/Z matched RTL-verification pilot

I took the first round where `branch_covered` = 24 and read the cumulative values at that round from `rounds`.

- **All 12 rows in `target_costs` match the `rounds` data exactly.** This covers tokens, cycles, executions and wall seconds.
- **I could not verify the SHA-256 values.** Only the embedded JSON was available, not the files.

## 2. Ceiling effects: the primary metric barely discriminates

- **The coverage path is identical in all 12 runs** through round 2:
  - Round 1: line 21/22, branch 20/24, expression 48/51, groups 4.
  - Round 2: line 22/22, branch 23/24, expression 51/51, groups 5.
- **Line coverage, expression coverage and fully covered groups saturate at round 2** in every run.
- **Branch coverage reaches 24/24 at round 3 in 11 of 12 runs.** The only branch-level difference anywhere is W rep 3, which arrives one round later.
- **The cost differences mostly reflect per-call token overhead, not search efficiency.** Because rounds-to-target are essentially constant, token cost works out to "tokens per call × 3."
  - The token ordering is already fixed in round 1, before any arms diverge in coverage: about 2.0k (W), 5.56k (X), 6.77k (Z) and 8.9k (Y) tokens.
  - Later per-round increments are about 2.4–3.1k (W), 2.8–3.1k (X), 3.1–3.5k (Z) and 3.7–4.4k (Y).
  - The roughly 2.1× Y/W token gap is therefore a prompt-size effect. It should not be read as feedback quality.
- **Wall time does not track tokens.** W has the lowest tokens but the highest wall time, even excluding rep 3 (mean of reps 1–2 is 20.1 s). Single-round latency spikes are large; for example, Z rep 3 took 8.9 s in round 3. Wall time looks dominated by API latency noise.

- **Baseline noise is already large.** Round-1 toggle coverage spans 61–72 even though branch coverage is identical everywhere.
- **Z has the widest spread**, a 32-point range at round 4.
- **Y nearly plateaus after round 2.** It gains +1, +1 and +12 in round 4.
- **Toggle was not pre-specified.** Treat it as exploratory only. Ranking arms on it would be post-hoc selection.

## 4. Arithmetic and accounting issues

1. **The cycle accounting does not match the stated limit.** The data fit a model where every execution replays the full accumulated stimulus, not just the 4-cycle seed:
   - The per-execution lengths would be 4, 12, 20, 28 and 36 cycles, which sum to 16, 36, 64 and 100.
   - Under this model, "cycles" grow roughly quadratically and overstate the stimulus actually generated.
   - This model is my inference. The packet should state the replay semantics explicitly.
2. **Z rep 1 shows 60 cycles at round 3**, against 64 everywhere else.
   - It is internally consistent with round 3 adding only 4 new cycles (60 → 92 at round 4).
   - It is therefore an under-used budget, not an arithmetic error. It does make the cycle cost unequal across matched runs.
3. **The `branch_covered_at_stop` label is wrong.** Runs continued to round 4 after hitting the target, and the costs are reported at first-target, not at stop. It should be renamed, for example `branch_covered_at_first_target`.
4. **Executions include an extra baseline run.** Round 1 already shows 2 executions, which implies a seed-only baseline run counted in the costs. The packet should document this.
5. **No arithmetic mismatches between files.** Wall times are monotone cumulative in every run.
6. **There is no failure data to analyze.** Calls always equal the round number, and failed attempts are 0 throughout.

## 5. What the packet cannot support

- **Checker validity.** Nothing shows that the 24 Verilator branch points or the testbench checks are correct or meaningful.
- **Feedback or prompt isolation.** The round-1 token gaps show that the arms' prompts differ, but the packet cannot show what differs or rule out leakage.
- **Generalization.** This is one small DUT (an 8-bit divider with 24 branch points). The target is too easy to separate arms.
- **Any statement about which arm received which feedback.** I have deliberately made none.

## Recommendations

- **Use a harder or non-saturating target.** Options include a larger DUT or a pre-registered toggle or functional-coverage goal.
- **Normalize or fix prompt overhead** so token cost reflects search efficiency rather than prompt size.
- **Report new-stimulus cycles separately from replayed cycles.**
- **Increase repetitions** before making any comparative claim.
