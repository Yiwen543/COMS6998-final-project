# Optional live pilot: scope-aware feedback in the next LLM request

This is a targeted **proof-of-concept** extension of the offline `egg_regression` benchmark. It does not alter the existing Milestone 3 live experiments or use new API calls by default. The scope is one actual T1 `data_last` violation monitor from the previously archived transaction API run. The archive's pinned member inventory is validated; the source is independently compared to the repository's original `data_last` reference in the unrestricted typed domain before any experiment begins.

## Task and qualification

Each arm starts from the exact same archived formula. Three predeclared maintenance stages require an equivalent literal-index refactor under `data_n = 4`, then `data_n = 5`, then `data_n = 4`. The syntax request is: include an equality between `data_index` and the current integer literal and do not retain `data_index == data_n` in either operand order. This is deliberately a controlled scoped-refactor objective, not a new RTL spec, and its very narrow task may exhibit a ceiling. A syntax pass alone is not a semantic pass.

Each response is accepted **only** when an independent full-width SMT comparison under the current guard establishes both alarm implications and the syntax objective passes. A true formula is an alarm, not normal operation. The active scope consists of two-state snapshots with declared unsigned widths. It is not proof of global equivalence, sequential RTL reachability, or general Verilog/SVA correctness. A SAT witness is an assignment in that typed scope, not necessarily an actual RTL state.

At every stage transition, the last qualified formula (or the previously carried one if the stage had no qualified attempt) is evaluated again under the new guard **before** the model receives the next request. A previous-guard proof is explicitly historical. A missing dependency blocks reusing that proof under a changed guard; it does not prove non-equivalence. The raw typed directional results determine actual semantic differences. Each arm receives up to `--attempts` requests per stage (1–3, default 2) and stops the stage immediately after a qualified response. Arm order rotates by stage; subsequent scope changes are mandatory.

| Arm | Actual user message sent to the provider |
|---|---|
| `raw` | Current guard, archived reference/candidate, previous-stage assessment, exact typed directional verdicts and replayed witnesses, syntax qualification |
| `ordinary` | Same mechanism plus certified context-scoped primitive facts and ordinary Boolean directional results |
| `egg` | Same mechanism as ordinary plus checked native rewrite steps (at most 8 shown per derivation/edge, explicitly marked if truncated), proof IDs, previously stored proof paths or blocked dependency reasons |

`egg_regression_feedback.py` derives primitive facts using `egg_regression_facts.py`, independently validates the receipts, compares with `OrdinarySession` and then uses the real `egg_regression_forms` binary. A persistent `ProofStore` is used within the egg arm. New proof edges are accepted only after independent native graph proof replay and typed-oracle consistency; old proof paths must be independently replayed under the active typed facts. Every prompt contains actual assessment data generated by this path, not an empty template. Full certificates, typed receipts, current guard and exact response are archived separately; a public prefix or proof ID is not a substitute for the private certificate.

## Commands

From the repository root, in the established project environment with `z3-solver` and Rust:

```bash
cargo build --release --locked --manifest-path egraph/Cargo.toml --bin egg_regression_forms
export EGG_REGRESSION_BINARY="$PWD/egraph/target/release/egg_regression_forms"
python3 scripts/egg_regression_live.py --fixture \
    --binary "$EGG_REGRESSION_BINARY" \
    --output /tmp/regression-live-fixture-$(date +%Y%m%d-%H%M%S)
python3 -m unittest discover -s tests -p test_egg_regression_live.py -v
```

If a project-specific `CARGO_TARGET_DIR` is set, use the resulting `$CARGO_TARGET_DIR/release/egg_regression_forms` binary instead. The default archive path is `results/milestone3/frame-txn-live/transcript.tar.gz`; override with `--archive` if needed.

After choosing a provider model and configuring `OPENAI_API_KEY` in the calling process (never save the key in a file or commit it), the explicit live entry point is:

```bash
python3 scripts/egg_regression_live.py --live \
    --model gpt-6.1-sol --reasoning-effort low --max-output-tokens 2048 \
    --attempts 2 --binary "$EGG_REGRESSION_BINARY" \
    --output /tmp/regression-live-$(date +%Y%m%d-%H%M%S)
```

This dispatches **at most 18 API requests**, at most two for each of three stages in each of three arms; as few as nine if every first request is qualified. The model selection must be supported by the caller's API project, and actual provider token charges vary. `--fixture` never dispatches an API request, even if a key is present. Provider errors preserve a partial result and do not report completion; invalid model candidates are recorded and cannot be qualified. The existing `egg_fifo_loop_provider.respond` function has no implicit retry. `config.json`, the independently qualified archived `seed.json`, each `preflight.json`, `attempt-*/request.json`, `response.json`, `assessment.json`, each stage summary, and the egg proof store are all emitted. `summary.json` distinguishes actual provider receipts and usage from fixture mode; no tokens are imputed for a fixture.

## Controlled fixture smoke test

The fixture deliberately supplies literal 4 at the first stage, a **stale** literal 4 at stage 2 attempt 1, a corrected literal 5 at attempt 2, and literal 4 again at stage 3. These are authored controls, **not outputs of a language model**. They exercise proof transport and invalidation, not the effectiveness of feedback at changing model behavior.

The local test completed 12 fixture responses, zero provider API calls and no token usage. Each arm qualified all 3 stages using 1/2/1 responses. In the egg arm, the stage-1 rewrite stored a checked proof; stage-2 preflight blocked that proof and both typed directional queries were SAT; the stage-2 next request contained the previous valid proof ID together with its current blocked dependency and typed witnesses. After the stage-2 correction, returning to guard 4 and the prior literal-4 formula reused the prior proof ID. The egg arm stored 2 checked proofs and invoked the native graph 5 times (including preflight and the repeated authored stale candidate). Tests explicitly inspect the serialized next-request message and compare ordinary/egg common facts, and exercise the injected-provider call boundary and receipt accounting using a test double, without network access.

This pilot does **not** establish improved repair rates, reduced token costs, end-to-end speed, or novel live model behavior. It is a prospective bounded API experiment entry point ready for local execution by the user; no real API experiment in this new pilot has yet run.
