## Research question and evaluation contract

Our proposal asks whether, under matched model and simulator budgets, e-graph-normalized feedback (C) improves generated verification stimulus over raw coverage feedback (B). Text/log-only feedback (A) measures the value of coverage feedback itself. The implementation fixes each DUT version, specification, checker, driver, Verilator instrumentation, initial sequence, raw coverage denominator, model, and round limits; the model emits validated cycle actions only. A receives logs and checker findings, B receives A plus all raw uncovered DUT counters, and C receives B's identical raw counters plus bounded, source-proven, two-state egg equivalence groups. C receives no solver witness or directed reference vector. The exhaustive/directed ceiling is kept out of prompts. These pilots evaluate *stimulus under a fixed checker*, rather than full free-form testbench or checker generation.

The primary outcome is cumulative **actual DUT coverage** after every complete stimulus batch, with tool-defined line/branch/expression/toggle counters retained separately. A raw counter is covered only when its own source location executes; equivalent predicates do not inherit each other's hits. We also record distinct checker-detected defect categories, invalid responses and retries, API input/output tokens, executed cycles including replayed initialization, simulator calls, compilation/simulation/egg time, and wall time. Token ROI is newly covered DUT branch points per 1,000 API-reported input-plus-output tokens for branch-targeted tasks (toggle points for toggle-targeted tasks). Cached and reasoning tokens are subsets of those totals. Reaching a predeclared coverage target and cost *at that point* are more informative than final percentage alone. Pass@1 across repositories is not estimable from three repetitions of one IP.

Verification quality needs four distinct gates: **validity** (legal stimulus, completed simulation, trusted checker); **coverage** (actual DUT counters plus declared functional bins, without silently dropping unreachable points); **fault sensitivity** (known-good controls pass, single-defect controls fail in the right category, distinct defects separated from repeated observations); and **efficiency/robustness** (tokens, cycles, simulator calls, time, failures and variance across tasks). High code coverage is neither proof that the DUT meets the specification nor proof that the testbench can find realistic faults. For our B/C causal question, the main estimand is a within-version difference in coverage trajectory and cost to a predeclared target, conditional on the same frozen checker and toolchain.

## Implemented evidence and present result

The repository contains real Verilator DUT-only counters, fixed specification-driven checkers, model-action validation, live OpenAI Responses API logs, and Rust `egg` equality saturation. The early arbiter/FIFO/timer adapters cover restricted Boolean guards; the held-out queue path uses Yosys pre-`proc` typed predicate extraction, complete activation guards, source joins, Z3-validated two-state rewrites, and 166-cell equivalence checks between two RTL versions (with the stated sampled-reset qualification). Unsupported expressions remain explicit and unmapped coverage points remain in the denominator. None of this is a four-state or arbitrary-SystemVerilog equivalence proof. The original faulty arbiter and timer RTL is preserved. Arbiter's repeated failures correspond to **two** distinct defect types (multi-bit override grant and asynchronous reset); timer timing failures correspond to the asynchronous-reset discrepancy. A correct checker identifying bad RTL is not a broken testbench.

All comparisons are descriptive, with only three repetitions per arm/version and no statistical-significance claim. C has **not shown a measured gain over B** in these pilots. It would also be incorrect to conclude that E-graphs cannot help verification: task simplicity, reachable-coverage ceilings, same-model action convergence, and restricted semantic coverage all limit discriminatory power. The queue result weakens the narrow hypothesis that *merely adding proved equivalence groups* guarantees improvement on this IP. It does not test richer state-aware feedback or generalization across IPs.

“The IPs are too small” is a plausible **part**, not a proved sole explanation. The arbiter is tiny, the FIFO branch counters are covered by the common seed, the timer has structurally constant toggle directions, and the queue's line target is reached by both arms in three rounds. Our fixed JSON action driver and supplied independent checker also remove much of the code-generation and oracle-construction difficulty measured by CVDP's full testbench tasks. A strong model can infer simple guards directly from raw RTL/coverage, while extra C text incurs token cost. Conversely, the queue's proved equivalent groups show that semantic redundancy alone does not guarantee a useful remaining decision after the model has already found the right actions. We need harder *reachable* predicates and independent IPs, not merely a larger source-file line count.

## Independent Claude Code review plan and acceptance criteria

Claude Code can provide a **second analyst**, not an independent measurement instrument. The independent ground truth remains a saved stimulus replay through the frozen driver, checker, simulator, and raw counter parser. We will give Claude Code read-only access to a frozen evidence bundle containing the proposal, exact DUT/spec/checker hashes, per-call actions, raw counters, prompt-difference audit, egg/Z3 proofs, and the draft report. To reduce confirmation bias, its first pass will use anonymous `X`/`Y` arm labels with the arm mapping withheld, then the labels will be revealed for attribution checks. The review asks it to seek discrepancies, not to improve stimuli or change the scorer.

Acceptance checklist: (1) replay agrees with reported per-round counters and failures; (2) `X`/`Y` share DUT, seed, driver, budget and raw counter arrays; (3) every C-only equivalence claim has a source span, complete activation guard, type/width context and proof; (4) no group transfers a hit to another source location; (5) token totals include retries once and do not add cached/reasoning subcounts twice; (6) target costs include all replayed cycles and executions; (7) interpretations distinguish a ceiling from evidence of no effect. Claude's narrative verdict alone cannot satisfy any of (1)–(6). Disagreements must be resolved against raw logs or an independently executed replay and documented, including unresolved ones.

## Next discriminating experiment

Before another paid pilot, pre-register an outcome-blind task screen. Require at least two *independent IPs* with multiple source-distinct, genuinely equivalent **uncovered** predicates, meaningful nested guards, a reachable target the shared seed and first raw-coverage round do not immediately saturate, and separately validated specification checkers. Keep every original raw counter; prove rewrites and equivalence-checked syntax variants under declared two-state semantics. Run B/C with matched settings and budgets (plus A as a coverage-feedback control where practical), independent sessions, three or more repetitions, and full per-round curves. Report target attainment, new coverage per token/cycle/simulator call/wall time, functional-bin and fault-detection results, and prompt overhead. A length-matched placebo semantic appendix would help distinguish useful grouping from additional text. Queue variants test syntax robustness but not cross-IP generalization; a deeper FIFO/controller with full/empty, simultaneous operations, wraparound, and reset during activity is a natural next candidate if its specification can support an independent checker. This follows the proposal's parsing → simulation coverage → semantic refinement → A/B/C evaluation flow without manufacturing a positive result.
